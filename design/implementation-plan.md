# 自动化测试平台实施计划

版本：v0.2｜日期：2026-10-24｜状态：按单一客户端重新规划

当前进度：第一块已形成可运行 GUI 骨架，并支持按类型、数量建立多环境组合；第二块提供组合初始化接口与离线演示，真实设备操作待内部实现；未完成完整首期交付。安装、测试及已实现范围见 [README.md](../README.md)。

配套设计：[architecture.md](architecture.md)。本计划面向用户评审和内部实现，以可演示的软件功能组织工作。旧版 P0～P6 和细碎任务编号不再作为执行计划。

## 1. 这次要交付什么

交付一个 Windows 客户端，遵循用户提供的布局：

**打开工作空间 → 选择并配置环境 → 保存 → 点击环境初始化 → 查看进度和结果。**

第一版完成环境初始化，不运行 Benchmark。“执行测试”和 Benchmark 方案区保留并标明尚未接入。后续测试功能必须先检查环境状态，未就绪时提示初始化，不自动烧录或重启。

EVB 优先打通，同时保留并实现既定的服务器初始化范围。DV 作为特殊环境由内部接入，不在外部讨论其含义或操作。

配置保存与执行是同一客户端内部能力。无需分别交付配置软件和执行软件，也无需用户手动传递配置文件。

## 2. 只按三块工作推进

| 工作 | 一起完成的内容 | 用户可以看到的结果 |
| --- | --- | --- |
| 一、客户端与工作空间 | 主界面、目录选择、测试类型占位、多环境组合与档案详情、配置保存/恢复、两个操作入口和状态区 | 能建立 2 个 EVB + 1 台服务器等组合，关闭再打开后继续使用 |
| 二、接通环境初始化 | 将已有启动与初始化过程接入按钮，包括版本文件、目标检查、日志、失败处理 | 在同一窗口一键完成真实环境准备，看到实际结果 |
| 三、整合试用与交付 | 在日常 PC 和真实环境中使用，修正交互、安装、配置和错误反馈问题 | 可由使用者按说明运行的客户端，以及简短使用说明 |

这是开发顺序，不是三个独立产品。界面和执行之间可以持续联调，不必等所有通用底层开发完才出现可用界面。

### 一、客户端与工作空间

按照草图实现一个主窗口，当前测试类型显示为“测试类型 1”，后续可以增加。环境组合采用动态列表：每次添加一项，再选择类型和具体环境档案；环境详情通过弹窗编辑。工作空间负责保存环境档案、本次组合和本机路径。Benchmark 先保留位置，不做完整配置系统。

第一次演示应能完成：选一个目录，建立至少两个同类型环境和一个不同类型环境，修改详细参数并保存，退出后再次打开，恢复刚才的组合和设置。

这一块同时约定初始化调用的输入与结果，使按钮和状态区能接收后台进度。若用模拟执行验证界面，必须明确标为演示，不能显示成设备实际初始化成功。

### 二、接通环境初始化

以一套典型 EVB 为第一个贯通对象，把已有流程整体接到“环境初始化”按钮：

**版本文件准备、配置/目标检查、已有脚本启动、串口网卡配置、SSH 软件部署及初始化、最终检查。**

这些动作是同一块工作内部的步骤，不再各自排成一个项目阶段。连接封装、日志、超时和错误反馈随实际接入一起实现；仅抽取已出现的共用能力。

EVB 跑通后，以相同方式接通服务器的电源、BIOS 参数及 SSH 初始化。DV 的配置和流程由内部系统按同一入口实现，不假定它等于服务器，也不要求它复制 EVB 的步骤。

本块演示从客户端选择环境开始，到环境真正可以测试结束。不能用“脚本启动了”或“OS 已启动”替代完整初始化结果。

若某环境尚未接入，应在界面明确显示不可用及缺少的内部实现。DV 是否列入首版可用环境，由内部按实际需求和适配进展确定；不能仅显示一个下拉框就声称支持。

### 三、整合试用与交付

使用真实的日常操作检验整个客户端：更换环境、选择版本、保存配置、初始化、查看失败日志、退出和再次打开。至少在另一台符合约定的 Windows PC 上验证安装与配置，避免依赖开发者的目录和设置。

修复影响使用的交互与异常问题，并给出客户端运行包或明确的安装启动方式，以及一份从工作空间配置到初始化完成的操作说明。

三块工作完成后才称为首版客户端交付。实际测试执行、中心调度或 AI 能力不加入这次交付门槛。

## 3. 用户只需验收这五件事

| 验收内容 | 判断标准 |
| --- | --- |
| 界面与操作 | 一个客户端内完成环境选择、配置和初始化，没有必须手动切换的第二个工具 |
| 配置复用 | 工作空间可选；环境详情和上次选择能保存恢复，不丢配置、不跨空间串用 |
| 真实初始化 | 已支持的 EVB/服务器流程完成最终就绪检查；DV 按内部确定的范围单独声明支持 |
| 过程与失败反馈 | 长时间运行时界面可响应；能看到进度、日志和失败位置；错误目标不被操作，失败后不自动重试破坏现场 |
| 首版边界 | Benchmark 和测试执行显示未接入；不会出现空按钮假成功或自动触发初始化 |

具体设备的成功条件和异常案例由内部实现人员验证，参考 [internal-integration.md](internal-integration.md)，不把每个底层检查都变成用户要管理的里程碑。

## 4. 怎样交给内部模型执行

先读 [architecture.md](architecture.md) 了解客户端形态，再按上述三块工作实施。[internal-integration.md](internal-integration.md) 只在接到对应环境时查阅；无需先逐项填完所有内部信息，才允许开始客户端开发。

建议每完成一块，提供能运行的客户端演示、简短的完成情况及尚未接通的环境。需要改变范围或使用方式时再与用户讨论。命令、端口、日志和 DV 的细节在内部询问。

通用模块和客户端已按后续授权在本仓库实现初版；设备操作在内部继续接入。不要把 GUI 演示和自动测试通过当成真实环境初始化验收。

## 5. 排期方式与后续工作

排期围绕上述三块工作安排，不给每个连接函数、日志字段或校验动作单独安排工期。具体天数应在内部查看已有脚本和客户端技术条件后，分别估算三块工作的投入；当前没有开发资源和脚本改造工作量依据，不将猜测写成承诺。

第一块主要取决于客户端实现与配置编辑；第二块主要取决于既有脚本能否直接调用、成功条件和 DV 的内部接入；第三块取决于真实试用发现的问题。每次评审直接看可运行结果，而不是完成了多少底层任务编号。

后续版本再接入一个真实 Benchmark，形成“初始化 → 执行测试 → 查看结果”的完整体验；之后按需要扩展多测试类型、监控分析、环境占用、无人值守及 AI 辅助。
