# 内部系统对接索引（草案）

主文档：[架构设计](architecture.md) · [实施计划](implementation-plan.md)｜关联讨论：[Codex 讨论](../talk/codex-discussion.md)

本文用于交给公司内部模型，补齐 EVB、服务器及 DV 的私有操作细节并实现适配层。它是实施时按需查阅的参考清单，不是项目排期，也不要求用户逐项管理。实际命令、地址、凭据和日志样例仅在内部维护。

当前产品为一个 Windows 客户端：配置与执行在同一窗口完成，工作空间保存和复用本地配置。第一版只完成环境初始化，Benchmark 和“执行测试”保留入口。旧文中“配置工具/执行工具”应理解为客户端内部职责，不是两个交付软件。

## 1. 内部模型的接手方式

1. 先读取 architecture.md 的首期范围和架构，再按 implementation-plan.md 的三块工作实施；接入具体环境时查阅本文件，不要求先补齐所有条目才能开发客户端。
2. 通过下面的稳定编号组织问题；先询问已有资料和实现，避免要求用户重复描述。
3. 对每项记录“待询问 / 已明确 / 已实现 / 已验证”，以及内部资料位置和验证结果。
4. 不得把示例字段或端点编号当成真实设备事实；未完成的必要检查必须阻止依赖步骤执行。
5. 优先调用已有启动脚本，不在未知其行为时重写烧录逻辑。
6. 本文的状态和结果字段是建议约定，可在内部完善；应同步更新配置工具和执行工具使用的约定。

首期服务器支持电源控制、BIOS 参数修改、SSH 软件部署和初始化；不支持 BIOS/BMC 固件更新或待测板卡固件更新。EVB 的烧录和 OS 启动由既有启动脚本完成。首期不因测试参数变化自动重启环境。

## 2. 建议的共同输入输出约定

| 类型 | 建议内容 |
| --- | --- |
| 步骤输入 | 运行编号、环境编号、已解析的目标信息、版本/文件引用、步骤参数、超时设置、日志目录 |
| 认证信息 | 通过内部定义的凭据引用获取；不要求明文写入可分享的任务配置 |
| 步骤输出 | 步骤状态、开始/结束时间、结果说明、错误类别、诊断证据引用、已执行的状态变更 |
| 步骤状态 | 成功、失败、超时、取消、明确不适用而跳过；运行中状态另行提供 |
| 未配置行为 | 缺少必要的核验或成功判定时，返回配置不完整并停止；不得作为“不适用”跳过 |
| 证据 | 相关日志位置、退出状态、只读检查结果；敏感信息需要脱敏 |
| 重试 | 首期不自动重放改变设备状态的动作；只读轮询可在定义的期限内重复 |

进程结束不等于业务成功；进程超时也不表示远端动作已经停止。每个适配项都需要说明它能观察和控制的范围。

### 2.1 EVB 内部实现边界（2026-10-27 补充）

EVB 的公共设计只使用稳定的逻辑名称，不在外部仓库中暴露以下内部信息。内部实现时需要补齐并维护对应关系：

| 公共占位 | 内部需要补齐的内容 |
| --- | --- |
| EVB 类型/平台 | 具体芯片代号，以及代号与版本目录、启动框架的映射 |
| `serial_a`～`serial_e` | 5 个串口的真实角色名称、用途、登录方式和启动脚本字段 |
| `firmware_archive` | 固件压缩包及其内部文件的真实命名规则 |
| `boot_script_archive` | 启动脚本压缩包、入口和可调用的接口 |
| 启动配置适配 | BMC 控制网口、EVB-GE、串口、本地库、PN 码等参数到启动脚本配置的映射；可评估使用 Jinja 模板，但模板只能来自受信任代码 |
| 环境上操作 | 驱动与第三方包上传后的具体安装、配置、初始化和成功判断 |

同一版本目录包含`firmware.zip`、`boot-script.zip`、`driver.zip`和`third-party.zip`四类逻辑制品；上述名称只是公共文档中的逻辑名称，真实文件名留在内部映射。EVB Model 通过窄的启动适配接口调用现有启动框架，不把私有配置字段散落到公共 Executor 或 Basic Connector 中。

当前已经确认：PN 码属于 EVB 环境长期配置，但允许用户从界面修改；FileZilla 服务根目录、用户名和密码属于每台执行机的本地设置，用户名和密码允许明文保存在工作空间；5 个串口需要从初始化开始前持续接收并保存日志；BMC SSH 不要求持续日志；EVB SSH 的持续日志采集由内部实现补齐。

BMC IP 是设备已经具备的连接地址，只需要传给启动脚本；EVB-GE IP 是启动过程中写入设备的目标地址，启动阶段成功后才能使用该地址建立 EVB SSH Connector。串口服务器使用共享模式，允许启动脚本与 5 个只读日志 Collector 同时连接。所有内部小步骤都必须作为所属 Phase 下的 Step 留下分层结果；每个 Step 的成功标志、失败标志和超时由内部受信任配置补齐。Plan 完成后仍执行一次独立、只读的最终就绪检查。

“本次测试工作空间”特指客户端主界面最上方由用户打开或新建的工作空间根目录，例如`F:\Codes\ebon_blade_tmp`。目录语义固定为三层：`<workspace>/versions/<平台>/<版本>/`是持久版本缓存；用户选择的`<workspace>/`是本次测试的工作空间范围，配置阶段把启动脚本、驱动和三方包准备到这里；FileZilla 根目录是工作空间之外的本机固定服务目录，只接收解压后的固件内容。不能把`runs/<run-id>`日志目录误称为用户所说的工作目录。

工作空间缓存中的原始固件 ZIP 必须保留。FileZilla 根目录不得留下固件 ZIP；优先直接从缓存 ZIP 解压到 FileZilla 根目录，如果内部工具必须临时复制 ZIP，解压后只删除该临时副本。EVB SSH 的端口、用户名和密码与 PN 码一起保存在 EVB 环境档案中，用户名和密码允许明文保存。

一次环境组合中的每个EVB分别在主界面选择版本；不同EVB可以使用不同版本。多个EVB选择相同`platform + version`时，远端备料只执行一次，后续EVB复用工作空间内的同一版本缓存。由于FileZilla根目录和工作空间准备目标会覆盖，各EVB仍按顺序初始化。

## 3. 对接条目

### INT-001：环境清单与本地设置

**内部需要询问**

- 环境编号的管理规则；现有 Excel 哪些字段分别表示身份、连接地址和其他配置。
- 谁维护连接地址变化，客户端如何获取环境清单，如何辨认配置的新旧。
- 用户所选工作空间如何保存环境详情、本机设置和上次选择；切换工作空间时如何隔离配置。
- 一个测试任务可以包含多个同类型或不同类型环境；内部流程如何接收完整组合并处理依赖关系。
- 本地 Python/启动框架、文件缓存、FTP 目录和日志位置怎样配置。

**需要实现**

- 以环境编号解析当前环境信息，并记录本次采用的清单版本或内容摘要。
- 区分共享环境信息、本地 PC 设置和本次任务选择。
- 客户端直接读取与保存工作空间，不要求用户导出配置再启动第二个程序；恢复历史配置不能默认设备仍然就绪。
- 环境档案与本次组合分开维护；执行前一次性检查组合中所有目标的适配能力，避免运行到一半才发现后续目标不可执行。
- 地址或配置变化后重新检查，避免旧任务文件中的地址被无条件复用。

**验证**

- E001 地址变化后能发现并使用正确配置；缺少必要字段时在设备操作前报错。

### INT-002：BMC 身份核验

**已知**

- SSH 登录的是管理卡自身系统，可通过 ifconfig 查看网卡 MAC。
- 用户描述 MAC 尾部与环境编号存在对应规则，但未给出完整规则或唯一性范围。

**内部需要询问**

- 哪张网卡是身份依据，如何从输出中准确定位；连接地址是否经过转发或映射。
- 如何获得并维护预期完整 MAC；管理卡更换时如何更新记录。
- 是否还需结合其他设备身份信息。

**需要实现**

- 只读读取实际身份，与独立维护的预期值比较，输出匹配、不匹配或无法核验及其证据。
- 不得将刚读取的 MAC 自动登记为预期值，也不得默认只比较尾部即可。

**验证**

- 正确设备通过；地址指错、MAC 不符、输出无法解析或网络不可达时阻止烧录/复位。

### INT-003：5 个串口端点与控制路径关联

**已知**

- 总计 5 个端口，BMC 与 EVB OS 串口不是同一端口；私有用途不在外部文档中描述。
- 公共设计暂以 `serial_a`～`serial_e`表示，内部实现时替换为真实角色名称。
- 5 个串口都要从 EVB 初始化开始前持续接收数据并保存原始日志，生命周期延续到本次运行结束。
- 串口服务器处于共享模式，允许启动脚本与日志 Collector 同时建立连接；日志 Collector 使用独立的只读会话。

**内部需要询问**

- `endpoint_1`～`endpoint_5` 分别属于什么角色，哪些步骤使用哪些端点。
- 登录方式、串口交互状态、是否允许多个客户端，以及谁持有连接。
- 怎样核对每条会执行命令的控制路径确实属于所选环境。

**需要实现**

- 在内部把逻辑角色映射到端点和启动脚本字段；编号本身不表示角色。
- 连接、日志读取和命令执行的协作方式，避免平台与已有脚本同时读写同一会话造成干扰。
- 如果没有技术手段核验某条路径，明确记录限制，并在内部确定补充核对或人工确认措施；不能宣称已自动验证。

**验证**

- 端点映射错误或未完成必要核验时，相关操作被阻止；串口日志可以追溯到具体端点和运行。

### INT-004：版本文件与 FTP 准备

**已知**

- 版本按测试目的选择；同一版本目录包含启动脚本、固件、驱动和第三方包四类压缩包，四者使用同一个版本号。
- 具体文件名属于内部信息，由内部适配层把四个逻辑制品映射到真实文件。
- 远端版本通过 Linux SSH/SFTP 拉取到当前工作空间的`versions/`目录；该下载过程不再依赖中心 FTP 服务。
- 固件压缩包需要解压到本机 FileZilla 对外提供的目录；启动脚本也需要解压后调用。
- 当前 FileZilla 与启动框架位于同一台 Windows PC。
- FileZilla 服务根目录、用户名和密码按执行机配置；用户名和密码允许明文保存在工作空间。
- FileZilla 根目录不按版本划分子目录。每次 EVB 初始化都先清空该目录，再将本次固件内容解压到根目录；启动脚本、驱动和第三方包不得放入该目录。
- 版本缓存中的原始固件 ZIP 不删除；FileZilla 根目录中不得残留固件 ZIP 或其临时副本。

**内部需要询问**

- 文件命名和目录规则；实际取文件的是谁、在什么阶段、持续多久。
- 是否支持不同目录或远端服务地址；固件、驱动、第三方包如何关联。
- 固定目录的替换范围，以及哪些文件必须保留。

**需要实现**

- 按版本定位四类文件，先准备到工作空间，再按启动流程需要解压固件与启动脚本。
- 文件准备完成后才开放后续启动步骤；失败时不将半份文件当作可用版本。
- 在固件可能被 FileZilla 读取期间禁止另一任务覆盖共享目录，并记录实际使用的版本和文件路径。
- 对同一个 FileZilla 根目录持有独占锁；从清空目录开始，直到启动框架确认不再读取固件之前，不允许另一项 EVB 初始化进入固件准备阶段。
- 版本来源与本机 FileZilla 提供方式分开：前者使用 Linux SSH/SFTP，后者只服务本次 EVB 启动流程。

**验证**

- 缺文件、复制失败、版本内容不符和同一服务目录被占用时，在启动前给出明确结果。

### INT-005：已有启动框架入口与目标配置

**内部需要询问**

- 现有框架的入口、配置格式、依赖、适用环境类型，是否已有或可增加命令行入口。
- 现有框架已有 GUI 和源码；优先确认是否可以提供稳定的 Python/API 调用入口，避免依赖 GUI 自动点击。
- 框架已负责哪些步骤，例如复位、取文件、烧录和启动 OS。
- 它是否还从其他文件读取 BMC/串口目标，退出程序是否影响设备或后台任务。

**需要实现**

- 将平台已解析、核验的目标信息和版本输入传给框架。
- 增加窄的 EVB 启动适配层，将公共逻辑字段转换为内部启动框架参数；模板和参数映射保留在内部受信任代码中。
- 确保框架实际使用的目标与平台核验目标一致；记录最终生效的配置。
- 尽量为每次执行使用独立配置；若必须改共享文件，在内部明确互斥和恢复方式。
- 不重复执行框架已经完成的烧录等动作。

**验证**

- 注入陈旧配置或缺失字段时能发现错误；所选版本和目标能追溯到实际调用。

### INT-006：启动日志与启动完成判定

**内部需要询问**

- 日志来源、编码、轮转方式；是否有结构化状态或退出码。
- 明确的成功和失败证据、正常启动耗时、超时规则。
- 每个内部启动步骤分别使用什么成功标志、失败标志和等待超时；不能只为整个脚本配置一个最终字符串。
- 启动进程返回后是否仍有后台或远端操作继续。

**需要实现**

- 采集本次启动相关日志，按内部证据判断成功、失败或超时。
- 避免把旧日志中的成功提示误认成本次成功。
- 未达到启动完成条件时不得进入网卡配置或软件部署。

**验证**

- 正常启动、明确失败、长时间无进展、进程已返回但设备未就绪，以及历史日志干扰等情况均有明确结果。

### INT-007：EVB 网卡配置与 SSH 就绪

**内部需要询问**

- 使用哪个串口角色、命令序列、交互提示和错误输出。
- 地址配置规则；重复执行是否有影响，断连后怎样判断执行结果。
- 目标 OS 的 SSH 地址、认证方式和必要的身份/就绪检查。

**需要实现**

- BMC IP 作为已经存在的连接地址传给启动脚本，不由公共 EVB Model 修改。
- EVB-GE IP 由启动阶段写入设备；只有启动阶段明确成功后，才允许根据该目标地址创建 EVB SSH Connector。
- 在启动完成后检查指定目标的 SSH 登录与就绪。
- EVB SSH 的端口、用户名和密码来自 EVB 环境档案；第一期允许明文保存。
- 不能只凭端口可连接就假定已连接正确且可用的 OS。

**验证**

- 网卡配置失败、错误地址、SSH 认证失败时停止，日志足以定位发生在哪一步。

### INT-008：软件部署、初始化及最终就绪

**内部需要询问**

- 驱动、第三方包的选择规则、传输目标、安装与初始化顺序。
- 初始化是否会重启、断开连接或影响下次执行。
- 退出码之外还需检查哪些状态，才能确认可以运行测试。

**需要实现**

- EVB 启动完成后，通过 SFTP 上传同版本的驱动压缩包和第三方包；随后执行内部定义的环境上操作。
- 传输、安装、初始化和最终检查各自记录结果；具体命令在内部定义。
- 给出可被测试平台读取的“准备成功/失败”结果和相关版本记录。
- EVB SSH 的持续日志采集由内部 Collector 实现；BMC SSH 第一阶段不要求持续日志。
- Plan 全部 Step 成功后，再执行一次独立、只读的最终就绪检查；具体命令和成功标志由内部实现。

**验证**

- 上传不完整、安装失败、初始化脚本返回但环境未就绪时，不得报告准备成功。

### INT-009：服务器电源与 BIOS 参数

**内部需要询问**

- 设备厂商/能力、可用 BMC 接口与认证方式；首选 Redfish 的可行性在内部验证。
- 服务器身份核验方法、电源状态判断、BIOS 参数读取/修改方式。
- 参数何时生效、何时需要重启、如何读取实际生效值。

**需要实现**

- 仅提供本期需要的电源操作和 BIOS 参数设置，记录修改前后值并检查生效结果。
- 按任务需要决定是否重启；不要对每次准备都固定增加一次电源循环。
- BIOS/BMC 固件更新和待测板卡固件更新不在本期能力范围内。

**验证**

- 请求被接受但修改尚未生效、参数不支持、认证失败、重启后未就绪等情况能明确区分。

### INT-010：SSH 跳板、传输与认证

**内部需要询问**

- PC 直连或经 A 访问 B 的连接方式；每一跳的认证方式。
- 哪些文件由 PC 上传到 A，哪些需要 A 与 B 之间传输。
- 凭据存放、主机身份核对、超时和断连处理约定。

**需要实现**

- 统一提供命令执行、传输及结果收集能力，同时保留不同网络拓扑的配置。
- 不以 PC 必须直连 B 为前提；不把串口 Telnet 与 SSH 的会话处理混为一谈。

**验证**

- 直连和所需的跳板场景分别验证；任一跳失败时能定位且不继续后续初始化。

### INT-011：超时、取消与保留现场

**内部需要询问**

- 启动框架运行中哪些动作可以停止，哪些不能中断。
- 关闭连接或终止本地进程是否会影响设备。
- 故障时必须保留的日志、文件、进程和设备状态。

**需要实现**

- 失败后停止调度后续步骤，保存已获得的证据，不自动重烧或重启。
- 如果远端动作可能仍在执行，明确报告“动作状态未知/仍在进行”，禁止自动重发。
- 区分停止安排后续步骤与强制终止当前操作；具体取消行为由内部明确。

**验证**

- SSH/串口断连、启动超时和用户取消后，没有隐式清理或恢复动作破坏现场。

### INT-012：DV 特殊环境接入

**已确认的边界**

- DV 是一种特殊环境，不预设为通用服务器。具体含义与实现留在内部，不在外部继续询问。
- DV 与其他环境是否联用，不在公共架构中预设。

**内部需要确定并实现**

- 需要保存的配置字段、环境记录和本地依赖。
- 与主界面环境选择、详情编辑及工作空间保存的映射。
- 初始化入口、前置检查、过程状态、日志和最终就绪条件。
- 涉及多个目标时的选择和执行关系，以及失败时的处理。

**验证**

- 保存后能恢复配置；实际初始化结果能在统一界面显示。
- 未接好时显示尚未配置，不默认继承 EVB/服务器步骤，不返回假成功。
- 在内部明确首版是否包含可用的 DV 适配；交付说明如实记录支持状态。

## 4. 内部实现参考顺序与交付检查

本节仅提示设备接入的依赖关系，不替代 implementation-plan.md 的三块工作，也不形成额外项目阶段。内部编号用于查找信息。

1. 先完成 INT-001～003、005～006 的信息收集，确定配置和目标核验链路。
2. 实现 INT-004～006，验证从选版本到 EVB 启动成功。
3. 实现 INT-007～008，验证完整准备结果。
4. 实现 INT-009 及所需的 INT-010，接入通用服务器。
5. INT-011 贯穿每一步，不留到无人值守阶段才处理。

DV 按 INT-012 在内部确定接入方式。对接完成时应提供内部配置样例、适配层说明、成功/失败验证记录和仍存在的限制。客户端界面与后台执行使用同一份字段定义及校验规则。

以上步骤是首期内部拆分，不是额外要求用户在外部讨论中公开私有资料。
