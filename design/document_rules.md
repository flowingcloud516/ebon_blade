# 设计文档与讨论记录规则

> **文档定位**：全仓库文档维护规范。
>
> **主要作用**：统一文档层级、文件头、内部补充、相对链接和讨论归档方式。
>
> **使用方式**：新增、移动或大幅修改Markdown前必须查阅并遵循本文。

状态：当前有效

最后复核：2026-10-28

## 1. 统一文件头

每份Markdown必须在一级标题后提供以下三项：

```markdown
# 文档标题

> **文档定位**：它属于哪一层、哪一类文档。
>
> **主要作用**：它解决什么问题、保存什么事实。
>
> **使用方式**：什么时候必须读，以及它是否是当前实现依据。
```

三项内容必须结合具体文档编写，不能全部复制相同的空泛描述。历史讨论必须明确标记“不是当前实现规范”；验证清单必须说明执行条件和敏感信息要求。

## 2. 三层设计

1. 系统级设计放在`design/system_design.md`。
2. 模块设计放在对应源码模块根目录，例如`src/env_driver/env_driver_design.md`。
3. 具体实现设计放在对应实现目录，例如`src/env_driver/evb/evb_driver_design.md`。

没有自然代码归属的跨模块专题，例如日志和制品版本，继续放在`design/`。

## 3. 内部补充

公共设计使用`*_design.md`；内部补充使用相邻的`*_design_internal.md`。内部文件只写相对公共设计的差异，并在开头链接公共设计，禁止复制全文。

## 4. 链接

系统设计链接模块设计；模块设计链接具体实现；具体实现提供返回上层设计的链接。仓库内Markdown使用相对路径，文件移动后必须修复所有入链。

## 5. 状态与术语

正式设计开头至少包含状态、层级和最后复核日期。空白或尚未设计的文件必须明确写“尚未设计”，不能让AI误认为其内容完整。

术语以正式设计和ADR为准。历史讨论中的旧称不需要篡改，但不能继续出现在当前代码和有效设计中。

## 6. Talk

`talk/`保存原始讨论和阶段总结，不是实现规范。外部讨论写入`talk/external/`，内部敏感讨论写入内网仓库的`talk/internal/`。稳定结论必须同步到正式设计。
